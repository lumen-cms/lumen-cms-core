# Next.js Storyblok Boilerplate

## Local development

Use Node.js 24 (`nvm use`) and the repository's pinned pnpm version. Install with
`pnpm install --frozen-lockfile`, then run `pnpm dev` at `https://localhost:3000`.
Next.js development commands use the built-in `--experimental-https`, as
recommended by [Storyblok's visual preview guide](https://www.storyblok.com/docs/quickstarts/nextjs/visual-preview).
Next.js generates local certificates in the ignored `certificates/` directory
and may prompt for your system password when installing its local certificate
authority on the first run. Open the preview URL in a separate browser tab first
and accept the certificate if prompted, then set that URL in Storyblok under
**Settings > Visual Editor > Default environment**.

The old `devs`, `dev-safe`, and `devss` commands have been removed; use `pnpm dev`
or one of the site commands below. No separate SSL proxy or manual certificates
are needed. Next.js development and
production builds use Turbopack. Storybook retains its separate webpack builder.

### Astro CMS development

Run the dedicated server-rendered Storyblok preview with HTTPS:

| Command | Local URL |
| --- | --- |
| `pnpm astro:cms bali` | https://localhost:4321 |
| `pnpm astro:cms planet` | https://localhost:4322 |
| `pnpm astro:cms upskill` | https://localhost:4323 |

These commands load the consumer's `.env` and `.env.local` from the sibling
`websites/packages/<consumer>` directory, then apply this repository's
`.env.<site>` overrides. Shell variables take priority. Set
`NEXT_PUBLIC_STORYBLOK_PUBLISHABLE_KEY`, `STORYBLOK_PREVIEW_TOKEN`, and the site's
usual CMS settings there. Set `LUMEN_PREVIEW_SECRET` to choose the preview entry
secret; otherwise the existing legacy entry secret remains in use.

The CMS config reuses `certificates/localhost.pem` and
`certificates/localhost-key.pem`, generated by `pnpm dev`. If they do not exist,
generate them once from the repository root (macOS):

```sh
brew install mkcert
mkcert -install
mkdir -p certificates
mkcert -cert-file certificates/localhost.pem -key-file certificates/localhost-key.pem localhost 127.0.0.1 ::1
```

Certificates stay ignored by Git. Open the HTTPS URL directly first to verify
browser trust. A `401` before entering preview is expected.

In Storyblok's **Settings > Visual Editor**, add a local preview environment
using the preview entry URL, for example:

```text
https://localhost:4321/api/preview?secret=YOUR_URL_ENCODED_PREVIEW_SECRET&slug=
```

Storyblok appends the story path. The endpoint establishes the preview session
and redirects to the story while preserving editor query parameters. Set the
home story's **Real path** to `/`. To test entry directly, append `home` after
`slug=`. If the iframe keeps returning `401`, check whether the browser blocks
third-party cookies for Storyblok; preview uses a `Secure; SameSite=None` session
cookie. Test block selection, unsaved text/style edits, and save/reload in the
editor.

The port is strict, so an occupied port fails rather than changing the URL.
Use `pnpm astro:cms bali --port 4331` to choose another port and update Storyblok
accordingly. `pnpm astro:site <site> dev` remains the public-site dev command;
production API/preview builds continue to use `astro.server.config.mjs`.

### Astro internal links

`CmsAnchor.astro` is the shared anchor for rich text, buttons, navigation and cards,
including custom `linkRenderer` overrides. The public integration enables Astro
hover prefetch for internal page destinations. Downloads, external links, anchors,
actions, new-tab links and preview links are excluded. Custom anchors can opt out
with `data-astro-prefetch="false"`; custom renderers should forward anchor attributes.

The page loaders resolve Storyblok link UUIDs against a cached published story
inventory, using the current slug instead of stale cached URLs. Locale routing,
queries and anchors are preserved. Preview keeps Storyblok's draft-resolved links.
Missing UUIDs retain their existing URLs. The `astro:site` runner also imports the
consumer's exact, locale-independent mappings from `redirects.js`, applying them
to legacy CMS links and generating Astro redirect pages. Same-origin absolute
links are supported, and query strings/fragments are preserved. This does not
infer a locale for unknown URLs; unmapped stale CMS links still produce warnings.
Next-specific parameter patterns require separate hosting configuration.

Full static builds warn about internal links with no matching output page, static
file or configured redirect. Warnings identify the source page, link label and
URL; the HTML is never changed. Enable strict CI validation with
`LUMEN_LINK_VALIDATION=error`, or configure the integration directly:

```js
lumenStoryblok({
  linkValidation: 'error', // default: 'warn'; 'off' disables validation
  knownLinkPaths: ['/account'], // destinations served outside the static output
})
```

Partial `LUMEN_SAMPLE_ROUTES` builds and preview/server builds skip this output
validation. It checks page availability, not fragment IDs or external websites.
Routes added after deployment and hosting-only rewrites must be listed in
`knownLinkPaths`. Client-fetched content is outside build-time validation.

Astro consumers register the CMS components once through the SDK integration:

```js
import lumenStoryblok from 'lumen-cms-astro/integration'

// Add to the public site's existing Astro config:
integrations: [lumenStoryblok()]

// In the separate SSR preview config, use this instead:
integrations: [lumenStoryblok({ preview: true })]
```

The integration supplies the official `StoryblokComponent` registry; public
builds disable the editor bridge. Keep using `Document.astro` and `Block.astro`
to retain themes, consumer overrides, and CMS layout semantics. The registry
is in `packages/lumen-cms-astro/src/lib/componentRegistry.mjs`; register ordinary
components there and use a small `components/blocks` adapter for slot composition
or content transformations. `pnpm astro:registry` checks registry coverage.

Preview uses `getPayload`, `storyblokEditable`, and `StoryblokServerData`. Only
small public Shopify catalogs are round-tripped to avoid repeating the external
catalog fetch during page edits. Global edits refetch; public pages emit no
server-data payload. The custom update event handler remains necessary for CMS
head styles and native-widget remounting.

Run `pnpm test:astro:bundles` to build and browser-test isolated production
pages, or append `bali`, `planet`, or `upskill` for three real pages from that
site. Reports in `.website-tests/bundle-audit/<site>/pages.json` contain actual
requested JS chunks, inline-script sizes, and computed gzip sizes. See
[the bundle audit](docs/astro-bundle-audit.md) for results and limits.

After building fixtures (`pnpm test:astro:bundles`), run `pnpm test:astro:tabs`
for a browser comparison against the actual Next.js React/MUI tab renderer.
Astro tabs use DaisyUI's native scroll-snap carousel plus a small controller,
with touch/mouse swiping, wraparound, manual keyboard activation, responsive
layouts, and adaptive height. Run `pnpm test:astro:carousels` for the corresponding
Next.js carousel comparison plus mobile lightbox/Shopify checks. Basic single-slide
sliders, lightboxes and product images use daisyUI carousel; Swiper remains for
effects, free mode, dynamic pagination and multi-slide/spaced layouts. The bundle
audit verifies that these advanced dependencies stay off the lightweight pages.
Shopify's checkout SDK loads only when checkout is clicked; browsing products and
using the cart do not fetch it. Bundle checks also reject Shopify runtime downloads
on pages without Shopify components and test checkout with intercepted requests.
FullCalendar, advanced Swiper and parallax runtimes load near the viewport;
calendars load only configured view plugins and their selected locale. Legacy
story-list code loads only when the client fallback requests data. The bundle
audit checks before/after activation, CMS remounting and reduced-motion isolation.

### Published story pagination and images

Published `Document.astro` pages now use `/api/story-list` automatically for
pagination and search. The companion `astro.server.config.mjs` build exposes
that route and Astro's `/_image` optimizer. The renderer loads the published
source page and its list configuration on the server, so newly discovered
remote images receive optimized responsive markup. The initial page remains
statically rendered. Preview documents retain their existing preview behavior.

For split static/Node deployments, forward **`/api/story-list` and `/_image`**
(including query strings) from the public origin to the companion Node server.
Use the same CMS, locale, image allowlist and public-directory configuration
for both builds. These public routes do not require a CMS preview session.
Other preview routes keep their session checks.

The local static server supports the same arrangement:

```sh
LUMEN_SERVER_ORIGIN=http://127.0.0.1:4322 node scripts/serve-astro-site.cjs bali 4321
```

Start the companion build's `server/entry.mjs` on port 4322 first, with the
site's usual environment. `astro dev` serves pagination directly. Independent
consumer apps can re-export `publishedStoryListEndpoint as ALL` from
`lumen-cms-astro/server/published-story-lists` at their own `/api/story-list`
server route. Consumers supplying per-document component/link overrides should
use `createStoryListEndpoint` with the same server-side context overrides and
pass that route as `storyListEndpoint` to `Document`.

Run `pnpm test:astro:story-images` for the static page → production API →
image optimizer browser regression. It uses a local CMS/image upstream and
checks newly discovered image bytes, responsive candidates, AVIF selection,
search/history, invalid requests, and absence of browser-side CMS requests.

### SEO migration verification

`pnpm test:seo:parity` compares the shared renderer with the actual legacy
components, Next Head deduplication, `next-seo` and the Next sitemap handler.
Preview `noindex,nofollow` is the deliberate exception to published-page parity.

Build the three reference samples with `pnpm astro:site <site> build --sample`
for `bali`, `planet`, and `upskill`, then run `pnpm test:seo:sites --fetch`.
This compares 90 published Next pages against built Astro HTML, plus every entry
in both sitemap endpoints. Captures and the detailed report stay in
`.website-tests/seo-parity/`. `pnpm test:seo:corpus` additionally runs the real
legacy components against the captured CMS payloads. All commands fail on a
mismatch or missing artifact. Build without `--sample` for deployment; a sample
build's sitemap intentionally still describes the whole published site.

The static build now emits both `/sitemap.xml` and `/api/sitemap`; ensure the
hosting configuration serves both as XML. Static sitemaps refresh on rebuild.
The audit covers page SEO metadata and sitemap contents; deployment redirects,
HTTP headers, untested routes, and full body-content parity need separate
migration checks. See [the verification record](docs/astro-seo-parity-review.json).

Run `pnpm lint` for Oxlint (including type-aware and React Compiler checks) and
Oxfmt validation. Use `pnpm lint:fix` for safe lint fixes and formatting, or
`pnpm format:fix` for formatting alone. See [the Oxc tooling guide](docs/oxc-tooling.md)
for rule coverage, warning adoption, and editor setup.

`pnpm install` also enables the versioned `.githooks/pre-push` hook for this
checkout. Before each push, it runs `pnpm check:react-doctor`: a full,
noninteractive scan using the latest React Doctor, blocking on warnings, errors,
or a failed scan. The command requires network access to resolve the latest CLI.
Run `pnpm run prepare` to enable the hook in an existing checkout, or

For everyday development, select a website with one command:

| Command | Local URL |
| --- | --- |
| `pnpm dev:bali` | https://127.0.0.1:3009 |
| `pnpm dev:planet` | https://127.0.0.1:3010 |
| `pnpm dev:upskill` | https://127.0.0.1:3011 |

Each command loads one private file containing the site's tokens and settings:
`.env.bali`, `.env.planet`, or `.env.upskill`. These files are ignored by Git.
Edit the selected site's file once instead of commenting settings in and out of
`.env`. Stop with Ctrl+C to switch sites; restart after editing settings.

Next.js automatically loads `.env`, `.env.local`, and files for its standard
`development`, `production`, and `test` environments. Project names are not
Next.js environments: do not set `NODE_ENV=bali` (or another project name).
The commands use `dotenv-cli` (`dotenv -e .env.<project> -- next dev --experimental-https`) to
load the chosen file before starting Next.js directly. `--no-expand` preserves
literal values, matching the previous loader. No custom launcher or reference-token
lookup is used. Shell variables take priority over the project file; Next.js's
standard env files provide any missing values. Keep only shared defaults there.
Each site keeps its own build cache under `.next-reference/<site>`.

Build a selected site with the same env file and output folder:

```bash
pnpm build:bali
pnpm build:planet
pnpm build:upskill
```

These commands run the existing `build` script, including its TypeScript check,
with the selected project's environment loaded for the entire build.

For a fresh checkout, create these ignored files using the site's credentials
and existing settings. Use the application's normal variable names:

```dotenv
STORYBLOK_PREVIEW_TOKEN="<space-preview-token>"
NEXT_PUBLIC_STORYBLOK_PUBLISHABLE_KEY="<space-public-token>"
# Add this site's language, root-directory, or other settings here.
```

Existing boolean settings commonly treat any nonempty string as enabled. Use
an empty value to disable those settings, rather than the string `false`.

This runs the core repo's existing Next.js application against the selected
Storyblok space. It does not load a consumer website's custom Next config or
components from `../websites`.

Plain `pnpm dev` serves HTTPS at port 3000: select the
Storyblok space tokens in the ignored `.env` file:

```dotenv
STORYBLOK_PREVIEW_TOKEN=<space-preview-token>
NEXT_PUBLIC_STORYBLOK_PUBLISHABLE_KEY=<space-public-token>
```

Spaces with different locale or folder structures may also need the
`NEXT_PUBLIC_ROOT_DIRECTORY` and locale settings used by their deployed site.
The named launchers leave the application, routing, and rendering logic unchanged.

Use pnpm consistently. When switching from Yarn, move the old `node_modules`
directory aside before installing; do not mix dependency layouts. Clear the
application's old `.next` build cache when switching bundlers, then restart the
development server to avoid stale chunk URLs.

## Core 2.0 / websites migration

Core 2.0 requires Node.js 24, Next.js 16 and React 19. Keep
`transpilePackages: ['lumen-cms-core']` in the consumer Next config: the package
ships TypeScript source. The shared config no longer installs a webpack hook or
uses `next-transpile-modules`. Its old development/production wrappers remain
compatible entry points that merge `transpilePackages`. Use `pnpm analyze` for
Turbopack bundle analysis.

The shared config also bundles `@mui/lab` so its tab providers use the same
Material UI context as the renderer during server rendering.

It enables `experimental.turbopackClientSideNestedAsyncChunking`, matching
Turbopack's production default in development. This avoids missing preload
chunks for nested dynamic slider imports on Next 16.4.3
([upstream issue](https://github.com/vercel/next.js/issues/99149)). Keep this
shared experimental setting when adding consumer-specific experimental options.

No custom `experimental.optimizePackageImports` list is needed. Next 16 already
optimizes `@mui/material`, `@mui/icons-material`, `date-fns`, and `react-use` by
default. Lab components and MDI icons already use direct subpath imports. The
core entry point is small and initializes the CMS component registry through
side-effect imports; add an optimization for it only after measuring a benefit
and verifying registration and lazy-component boundaries. See the
[Next.js option reference](https://nextjs.org/docs/app/api-reference/config/next-config-js/optimizePackageImports).

Internal imports now resolve within the package. Consumers no longer need
`@CONFIG`, `@SSR_CONFIG`, `@LmComponentRender` or `@context/*` aliases, or paths
into a hoisted `../../node_modules` directory. Configure the exported `CONFIG`
and component registry through the normal `lumen-cms-core` imports.

The sibling `websites` repository uses pnpm workspaces and a shared
`tsconfig.base.json`. Each website runs a strict TypeScript check before building;
build errors are no longer ignored. Its production dependency is the published
`lumen-cms-core@2.0.0`, never a link to this checkout.

Release order:

1. Review and publish core `2.0.0`. The existing registry version `1.11.1` targets
   Next 13 / React 18 and cannot be substituted for this migration.
2. In `websites`, move the old Yarn `node_modules` directories aside, run
   `pnpm install`, and commit the resulting `pnpm-lock.yaml` with the migration.
   A registry lockfile cannot be generated until core `2.0.0` is published.
3. Run `pnpm check-types`, then the website builds. Configure deployment to use
   Node 24 and `pnpm install --frozen-lockfile` from the workspace root.

To verify before publishing, `scripts/prepare-consumer-verification.cjs` accepts
a `pnpm pack --out <archive.tgz>` archive and creates an isolated pnpm workspace
for all 12 consumers (or one selected directory). This verifies package contents
and isolated dependency resolution without changing production dependency URLs.

When upgrading an existing deployment, rename `NEXT_PUBLIC_PUBLIC_TOKEN` to
`NEXT_PUBLIC_STORYBLOK_PUBLISHABLE_KEY`, `NEXT_PUBLIC_PREVIEW_TOKEN` to
`STORYBLOK_PREVIEW_TOKEN`, and `NEXT_PUBLIC_SHOPIFY_ACCESS_TOKEN` to
`NEXT_PUBLIC_SHOPIFY_STOREFRONT_PUBLISHABLE_KEY`. Keep their values unchanged;
the preview token must stay server-only.

## Security migration: browser credentials

Use `STORYBLOK_PREVIEW_TOKEN` instead of `NEXT_PUBLIC_PREVIEW_TOKEN`.
Preview credentials are read only on the server; never serialize `CONFIG` into
page props. Browser list/search requests now use published content, including
inside the editor. Server-rendered previews remain available; fetching additional
draft content in the browser requires an authenticated server endpoint.
`NEXT_PUBLIC_PREVIEW_MODE` no longer switches the public token to a preview token.

Rename `NEXT_PUBLIC_PUBLIC_TOKEN` to
`NEXT_PUBLIC_STORYBLOK_PUBLISHABLE_KEY`, using a Storyblok **Public** token that
can read published content only. For the legacy Shopify config, use
`NEXT_PUBLIC_SHOPIFY_STOREFRONT_PUBLISHABLE_KEY` instead of
`NEXT_PUBLIC_SHOPIFY_ACCESS_TOKEN`, with a **public Storefront** token, never an
Admin or private Storefront token. Instagram API URL creation is server-only;
rename `NEXT_PUBLIC_INSTAGRAM_ACCESS_TOKEN` to `INSTAGRAM_ACCESS_TOKEN` and do
not send the resulting credential-bearing URL to browsers.

Update deployment environments before rebuilding. Rotate preview credentials
present in previously deployed Next.js or Storybook bundles, rebuild/redeploy
those applications, and retire old hosted artifacts and source maps. The local
comparison builds are historical evidence and do not update when source changes.

## Security migration: CMS click actions and product descriptions

The `on_click_function` CMS field now selects a named application handler. It no
longer executes JavaScript snippets. Register handlers during application setup,
then put only the matching name (for example `open-contact`) in the CMS field:

```tsx
import { cmsClickActions } from 'lumen-cms-core'

cmsClickActions.set('open-contact', () => {
  document.getElementById('contact')?.scrollIntoView()
})
```

Unregistered names and legacy JavaScript snippets do nothing; ordinary links
and explicit React `onClick` props retain their behavior. Migrate existing CMS
snippets into application code before deploying. Registered actions are public
UI behavior, not an authorization mechanism, and must not close over per-request
server state.

Shopify descriptions preserve text, headings, lists, tables, safe links, and
images. Scripts, event handlers, styles, embedded frames, SVG, and unsafe URL
schemes are removed before rendering, both on the server and in the browser.

## Iframe sandbox policy

CMS embeds are sandboxed independently of their existing `allow` feature policy
and fullscreen setting. Unknown URLs and same-origin pages may run scripts,
submit forms, and present media, but receive an opaque origin and cannot open
popups or navigate the parent page. Storage-dependent new providers require a
code review of `src/components/iframe/iframeSandbox.ts` before being added.

The exact HTTPS origins used by the reference sites have explicit permissions:

| Provider | Additional permissions and purpose |
| --- | --- |
| YouTube and YouTube nocookie | Normal origin for player storage, presentation, and popups for provider links |
| Google Docs/Forms | Normal origin for form/session behavior, forms, and popups for sign-in links |
| StudentsGoAbroad application portal | Normal origin, forms, popups, and document downloads |

Provider popups may escape the sandbox so their destination pages and sign-in
flows work normally. The embedded page itself still cannot navigate the parent.
These are trusted-provider exceptions, not isolation from malicious behavior by
those providers. The scripts/origin permission pair is never granted when the
provider origin equals the parent origin, and subdomains, lookalike hosts, HTTP,
and non-default ports do not inherit trust. CMS content cannot set the policy.

The GTM `noscript` iframe grants only `allow-same-origin`, preserving its normal
origin and image-based requests without allowing scripts, forms, popups, or
parent navigation. The JavaScript GTM path is unchanged. Browser consent,
tracking-prevention, and third-party-cookie policies still apply.

## Storyblok component workflow

The intended workflow is:

1. Update or add a component in Storyblok.
2. Pull the schema with `pnpm fetch-storyblok-components`.
3. Generate TypeScript types with `pnpm gen-ts-schema`.
4. Implement or update the React renderer using its generated content type, and
   register it under the Storyblok component name.

The CMS schema is the source of truth for content types. `pnpm gen-ts-schema`
runs the official CLI, then indexes its declarations into
`src/typings/storyblok/types/82895/registry.ts`. Added, renamed, and removed
components automatically update the registry's types; there is no manual content
union to maintain. The index references the CLI interfaces without copying fields
or modifying its output, so custom field types and application augmentations remain
available.

You still implement and register the React renderer manually. Generation cannot
choose which React component should render a CMS block. TypeScript checks that
each registration accepts the correct content props.

### Generated component types

Run `pnpm fetch-storyblok-components` after changing the CMS schema, then
`pnpm gen-ts-schema`. Both scripts call the pinned official Storyblok CLI directly.
The checked-in schema lives in `src/typings/storyblok/components/82895/` and
untouched CLI declarations in `src/typings/storyblok/types/`. Generation is local;
fetching requires CLI authentication. Pulling also refreshes group/preset metadata.

`generate-ts-schema-custom-types.js` supplies the custom field mappings. Application
metadata and legacy fields remain in `src/typings/storyblok-extensions.ts`.
Existing `typings/generated/components-schema` imports remain supported by a type
re-export. Numeric CMS fields use the CLI's `string` type; convert them to numbers
when calculating values. Do not edit generated declarations.

`pnpm check:storyblok-types` regenerates types, checks the generated files against
Git, and runs TypeScript. Run it after committing intentional schema/type updates.
The unit suite checks that every schema component and content field has an explicit
generated declaration, including all custom fields.

### Typed renderer registration

`LmCoreComponents` has a schema-specific renderer type for each of the 141 CMS
components. Assignments and overrides must accept that component's content.
`LmComponentRender` also checks content fields and parent-provided props, such as
card-list options, accordion state, and swiper options. Lazy and memoized renderers
use the same contracts. Provider/link hooks are typed separately from CMS names.

Prefer the checked helpers for registration, especially for batches:

```tsx
import { registerStoryblokComponent, registerStoryblokComponents } from 'lumen-cms-core'
import { LmButton } from './Button'
import { LmImage } from './Image'

registerStoryblokComponent('button', LmButton)
registerStoryblokComponents({ image: LmImage })
// registerStoryblokComponent('button', LmImage) // Type error
```

For consumer-owned CMS blocks generated from a separate schema, augment the
component map with the generated type (blocks in the core schema are discovered
automatically):

```ts
import type { PromoStoryblok } from './generated/storyblok'
import type {} from 'lumen-cms-core/src/typings/storyblok-registry'

declare module 'lumen-cms-core/src/typings/storyblok-registry' {
  interface StoryblokComponentMap {
    promo: PromoStoryblok // Must declare component: 'promo'.
  }
}
```

If a custom renderer requires props beyond `content`, also augment
`StoryblokRendererPropsOverrides` with its full props type under the same name.
The registry remains partial because deployments select their own renderers and
many schema blocks are configuration data. Unregistered blocks retain the visible
missing-component fallback. Avoid `Object.assign` for registration: its standard
TypeScript signature does not check source properties against the target; use
`registerStoryblokComponents` or `satisfies StoryblokRendererRegistry` instead.

Run `pnpm test:storyblok-registry` to check automatic discovery against an isolated
CLI schema, including schema additions/removals and generated content type errors.
