# Storyblok fetching migration — 27 October 2026

Branch: `feature/mui-v9`. Content fetching now uses the stable
`@storyblok/api-client` 0.9.1. React and rich-text rendering are unchanged in this
batch. Screenshots remain paused. This is a server-data compatibility check,
not browser visual or authenticated editor acceptance.

## Service compatibility

`StoryblokService` retains its `getStory`, `getStories`, `getAll` and rich-text
facade. Every content/space/overflow request uses the new client's resource
methods. `storyblok-js-client` remains a dependency for existing public TypeScript
contracts and as a test oracle; the service no longer instantiates it. The
stable React SDK also still depends on the older client transitively.

The adapter preserves response metadata (`data`, `perPage`, `total`, headers),
ordered pagination, nested filter queries, language selection, draft/public
tokens, release IDs, resolved links, and serializable nested relations. The
new client's automatic relation inlining is deliberately disabled: it can
create circular references, while Next.js props must be JSON serializable.
The compatibility resolver preserves the previous bounded expansion,
`_stopResolving` markers and link `.story` fields. Unit tests compare this shape
with the previous SDK, including mutually referencing relations and overflow
UUID responses.

Published settings/full-list caches are keyed by token, version, locale, release
and complete nested parameters. Concurrent full-list requests share work;
callers receive independent copies. Draft requests are not retained in those
caches. Cache versions are scoped to each token. The redundant process-global
category cache was removed, since it could return another site's/language's
categories; the scoped service cache supplies reuse.

Preview/release context is now request-local, including component-data hooks.
A WeakMap associates fetch metadata with that page's props object without
serializing it to the client. A preview load cannot turn subsequent public
loads into draft requests. The explicit `setDevMode`/`setQuery` methods remain
available for existing callers but the Next page loader no longer mutates them.

HTTP 404 still yields a missing page. Authentication, network and exhausted
retry failures propagate and fail a build instead of being cached as empty
content or misreported as a 404. The page resolver uses `Promise.all`, so it
cannot discard rejected fetches. Legacy list hooks also propagate failures.

The initial planet.training build exposed a shared-token 429 limit across its
nine Next workers. Each client now starts at four requests/second, with adaptive
backoff and five retries (including timeouts). Automatic CDN-cache acceleration
and server-header rate increases are disabled. This leaves headroom below the
observed 50 requests/second origin quota for these builds; larger concurrent
fleets may need a shared limiter.

References: [API client](https://www.storyblok.com/docs/libraries/js/content-delivery-api-client),
[Next getStaticProps](https://nextjs.org/docs/pages/api-reference/functions/get-static-props).

## Repeatable server-data checks

`yarn test` includes transport-mocked unit tests using the real clients and the
actual `pagesGetStaticProps → getPageProps → component-data hooks` pipeline.
The three sites' configured languages are exercised on home and deep routes,
including planet.training's settings overrides. Complete serialized props are
compared with the previous SDK, rather than only checking a component count.
Synthetic fixture content contains no credentials or captured customer data.
Additional checks cover pagination, resolved links/relations, filter cache
isolation, preview releases, missing pages, retries and failures.

The offline build-data regression gate compares all routes generated by the
real consumers with their own environment files:

```sh
yarn test:page-data \
  /tmp/lumen-consumer-storyblok-types \
  /tmp/lumen-consumer-storyblok-api-final \
  /tmp/lumen-api-page-data-final.json
```

This reads `.next/server/pages/**/*.json`, checks route-set equality, and hashes
canonicalized **complete page props**. It also compares component, array-item,
related-story, list-item and form-field counts. Only two proven per-load values are normalized: numeric
`*.list_widget_data.cv` (the existing widget writes `Date.now()`) and a nonempty
numeric `*.form_data.fbzx` token. Two read-only GETs of the same Google Form
confirmed that the latter changes between loads; no form was submitted. Missing,
empty or malformed tokens are still detected. Storyblok content versions, form
fields, content, IDs, order, list totals, and all other values remain checked. Differences report paths without printing
payloads or credentials. Missing builds fail; this command never accepts or
rewrites a baseline. CMS edits between builds legitimately fail this comparison
and must be investigated rather than automatically accepted.
